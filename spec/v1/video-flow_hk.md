# AI 影片生成流程 — 完整實施計劃

**版本：** 1.1（需求大幅擴充）  
**日期：** 2026-08-19  
**目標：** 透過受控、低成本、多代理、人類參與的流程，將已完成的故事線 + 每個場景的拍攝指示（包含部分 YouTube 參考片段）轉化為一段已完整製作、支援多種語言、可供 YouTube 發佈的影片。

> **v1.1 變更註記：** 第 1 節（需求）先前對製作用途而言過於高層次。現已使用正式綱要、量化一致性閾值、代理行為合約、精確交付規格、成本／審核規則、可量度的成功準則及明確的非目標重寫。

---

## 1. 詳細需求規格（增強版）

> **上一版本評估：** 原有需求具備功能性，但對於正式環境使用而言規格不足。當中缺乏量化門檻、正式的輸入／輸出綱要、故障模式、審計要求、成本預算、本地化邊緣情況，以及代理行為合約。以下章節將每個範疇擴展為可強制執行的工程準則。

### 1.1 輸入要求（嚴格綱要）

#### 1.1.1 故事線文件
必須以結構化資料（JSON 或 YAML）提供，並至少包含：

| 欄位 | 類型 | 必需 | 說明 |
|-------|------|----------|-------------|
| `title` | string | 是 | 暫定標題 |
| `logline` | string | 是 | 一句話前提 |
| `genre` | string[] | 是 | 主要 + 次要類型 |
| `target_duration_sec` | number | 是 | 預期最終片長（不包括包裝） |
| `aspect_ratio` | string | 是 | 例如 `"16:9"`, `"9:16"`, `"2.39:1"` |
| `target_platform` | string[] | 是 | 最低要求為 `["youtube"]` |
| `acts` | array | 是 | 按序列出的幕次及其情感目的 |
| `characters` | array | 是 | 標準角色清單（id、名稱、角色、年齡範圍、主要特徵） |
| `locations` | array | 是 | 標準場景清單 |
| `themes` | string[] | 否 | 用作風格指引的敘事主題 |
| `tone` | string | 是 | 整體基調（例如「電影感武俠、憂鬱、高對比」） |
| `language_primary` | string | 是 | `"yue"` / `"zh-Hans"` / `"en"` 等 |
| `notes` | string | 否 | 導演備註、限制、禁忌 |

#### 1.1.2 拍攝指令綱要（每個鏡頭）
每個鏡頭必須符合：

```json
{
  "shot_id": "S03-02",
  "scene_id": "S03",
  "order": 12,
  "duration_estimate_sec": 4.5,
  "narrative_purpose": "Reveal the antagonist's true identity through a slow push-in",
  "when": "After the protagonist opens the wooden box",
  "what": [
    {
      "type": "character",
      "entity_id": "char_antagonist",
      "action": "turns slowly toward camera, eyes narrowing",
      "emotion": "cold recognition"
    },
    {
      "type": "prop",
      "entity_id": "prop_jade_seal",
      "state": "held in left hand, partially obscured by sleeve"
    }
  ],
  "how": {
    "shot_size": "MCU → CU",
    "camera_angle": "slight low angle",
    "camera_movement": "slow push-in 15%",
    "lens": "85mm equivalent",
    "lighting": "single hard key from upper left, deep shadows",
    "color_intent": "desaturated teal shadows, warm skin highlight",
    "sound_design_notes": "diegetic wind + low drone swell"
  },
  "references": [
    {
      "url": "https://youtube.com/shorts/xxxx",
      "relevant_portion_hint": "middle 40% of the short, the close-up face turn",
      "notes": "Ignore the product placement at start and end logo"
    }
  ],
  "constraints": ["no modern objects", "period costume only", "no text on screen"],
  "priority": "hero"   // "hero" | "supporting" | "broll"
}
```

所有 `entity_id` 值必須對應至視覺聖經（第 2 階段）中的條目。在開始任何生成程序前，Orchestrator 必須拒絕缺失或含糊的欄位。

#### 1.1.3 參考影片限制
- 可接受的參考資料最長：180 秒（較長影片必須由使用者預先裁剪，或由擷取代理在取得明確的人手確認後裁剪）。
- 只支援可公開存取的 YouTube 影片（或使用者提供的本機檔案）。
- 系統在處理後，絕不可儲存長於所擷取相關片段的完整原始 YouTube 影片。
- 使用者必須聲明，參考資料僅在合理使用／轉化使用的假設下使用，目的僅限風格與構圖參考。流程不會複製音訊或具鮮明辨識度的受版權保護音樂。

### 1.2 輸出要求（精確交付物）

#### 1.2.1 主影片檔案
- 容器：MP4
- 視訊編碼器：H.264（High Profile）或 H.265（Main10）— 可由使用者選擇
- 解像度：1920×1080（預設）或 3840×2160
- 幀率：24 / 25 / 30 fps（鎖定至專案設定，不可混用幀率）
- 位元率目標：最終母版 ≥ 12 Mbps（1080p）/ ≥ 35 Mbps（4K）
- 音訊：AAC-LC、48 kHz、立體聲或 5.1（如音樂分軌支援）
- 色彩空間：除非明確要求 HDR，否則為 Rec.709（SDR）
- 必須包含與場景邊界相符的內嵌章節

#### 1.2.2 語言與字幕版本
必須生成三個完整的口語版本：
1. 英語
2. 普通話（普通話，中國大陸發音）
3. 廣東話（香港／廣東標準，任何螢幕文字均使用繁體中文）

字幕要求：
- 為全部三種語言提供軟字幕軌（`.srt` 或 `.vtt`）
- 可選提供燒錄字幕版本，供會移除軟字幕軌的平台使用
- 時間準確度：相對口語音訊 ±2 幀
- 最多兩行，建議每行 42 個字元
- 樣式不得與視覺語言衝突（字體、大小、位置、外框均於專案風格指南中定義）

#### 1.2.3 封裝元素（強制順序）
1. 精華／預告（8–20 秒，最精彩時刻，如有最終反轉則不得劇透）
2. 片頭標誌／片頭短片（2–5 秒）
3. 主要內容
4. 片尾名單／製作人員名單
5. 彩蛋（可選，3–12 秒，於片尾名單後）
6. 最終片尾卡／靜態或動畫圖像（3–8 秒）

#### 1.2.4 YouTube 中繼資料套件
必須包括：
- 標題（≤ 100 個字元，已最佳化）
- 簡短說明（≤ 200 個字元）
- 詳細說明（包含時間戳記、連結、hashtag）
- 章節標記（精確秒數）
- 標籤／關鍵字
- 縮圖（1280×720、高對比度、如有文字則須清晰易讀）
- 片尾畫面元素建議
- 如適用，播放清單／系列中繼資料

#### 1.2.5 製作稽核套件
系統必須為每個已完成的專案匯出一個完整的稽核套件，內容包括：
- 所有已使用的提示詞（包含模型、seed、temperature、timestamp）
- 所有中間資產（線框圖、關鍵幀、被拒絕的拍攝版本）
- 評審分數及完整回饋文字
- 附有時間戳記及鏡頭 ID 的人工回饋記錄
- 每段最終剪輯片段及主檔的資產雜湊值（SHA-256）
- 模型版本字串及本機環境快照
- 成本估算明細（本機 GPU 小時數 + 商業 API 點數）

### 1.3 一致性要求（量化）

此等閾值由連續性監督員代理執行。未能符合者將無法通過相關關卡。

| 維度 | 指標 | 最低閾值 | 衡量方法 |
|-----------|--------|-------------------|--------------------|
| 角色面容身份 | ArcFace / InsightFace 餘弦相似度 | ≥ 0.72（相同身份） | 將相同 `entity_id` 的所有人臉裁切圖與已鎖定的護照參考資料作比較 |
| 角色整體外觀 | CLIP 圖像對圖像相似度 | ≥ 0.78 | 全身或中景鏡頭嵌入 |
| 關鍵道具身份 | CLIP + 可選的物件偵測器嵌入 | ≥ 0.80 | 裁切的道具與護照作比較 |
| 地點／背景 | CLIP + 空間佈局特徵 | ≥ 0.70 | 同一地點的遠景鏡頭 |
| 全域風格／色調 | 色彩直方圖 + CLIP 美學嵌入距離 | ≤ 0.35（距離） | 專案層級的風格嵌入與每個鏡頭作比較 |
| 照明方向一致性 | 估計光線向量角度差異 | 相同地點的相鄰鏡頭之間 ≤ 35° | 本地照明估計模型 |
| 鏡頭之間的時間連續性 | 光流幅度不連續性 + 評審分數 | 不得出現無法解釋的明顯跳變 | 評審 + 簡單動作分析 |

任何鏡頭在用盡最高容許重新生成次數後，如仍未能通過上述兩項或以上指標，必須升級至人工審核。

### 1.4 質素關卡及流程要求

#### 關卡 A — 線框圖動態分鏡批准（硬性關卡）
- 必須在調用任何商業影片模型之前進行。
- 交付項目：單一可播放的動態分鏡（黑白或有限色彩），具備大致時間安排及暫用音訊。
- 人工必須按每個鏡頭 ID 明確批准、拒絕或要求修改。
- 如無已記錄的批准事件，系統不得進入第 5 階段及以後。

#### 關卡 B — 片段挑選批准
- 人工會在語境中審閱所選的影片素材。
- 可按新增限制強制重新生成個別鏡頭。

#### 關卡 C — 最終母帶批准
- 完整審閱畫面 + 所有語言音軌 + 字幕 + 封裝。
- 必須在生成發布套件前簽署批准。

#### 額外流程規則
- 每個鏡頭最多可自動重新生成 4 次，其後必須升級至人工處理。
- 所有變更已鎖定護照的代理決定均須使用新版本號，並重新驗證相依鏡頭。
- 評審代理必須回傳結構化 JSON（分數 + 自由文字理據 + 建議的提示詞改動）。僅含自由文字的回饋會被拒絕。
- 優先使用本機運算處理：參考資料擷取、關鍵影格描述、線框圖生成、動態分鏡組裝、連續性評分、基礎 TTS、字幕生成。
- 僅可將商業模型用於最終主打影片生成，以及本機品質不足時的高質素語音複製。

### 1.5 代理行為合約

| 代理 | 必須 | 不得 |
|-------|------|----------|
| 編排器 / 創意製作人 | 維持全域上下文、執行視覺聖經、路由工作、記錄所有決定 | 未經人工批准，虛構新角色或地點 |
| 鏡頭設計師 | 製作嚴格遵從護照及原始指示意圖的描述和線框圖 | 更改鏡頭的敘事目的 |
| 連續性監督員 | 使用量化指標，按已鎖定參考資料為每個實體評分 | 覆蓋人工批准決定 |
| 評審委員會 | 回傳結構化分數 + 可行的回饋 | 批准未通過硬性一致性閾值的鏡頭 |
| 風格總監 | 保護全域色調、顆粒感、鏡頭語言 | 在視覺聖經鎖定後引入新的美學元素 |
| 組裝代理 | 將 Remotion（或同等工具）程式碼維持為唯一真實來源 | 硬編碼無法編輯的時長 |
| 本地化代理 | 保留跨語言的情感意圖及時間安排 | 虛構原始劇本中不存在的對白 |

### 1.6 非功能性及營運要求

- **可重現性**：在使用相同已鎖定的視覺聖經、相同提示詞、相同種子及相同模型版本的情況下，管線必須能在正常生成變異範圍內重新生成任何中間資產。
- **成本預算意識**：系統必須在開始第 6 階段前估算並顯示預計商業額度成本。用戶可設定硬性預算上限。
- **本機資源意識**：偵測可用 VRAM，並在必要時自動選擇量化模型或卸載策略。
- **私隱**：參考影片及中間影格絕不離開本機，除非用戶明確啟用需要上載的商業模型。
- **故障模式**：網絡故障、模型逾時、低相似度分數及人工拒絕均必須妥善處理，提供清晰的復原路徑，且不會出現無聲資料遺失。
- **可審計性**：每項狀態變更均附時間戳記、代理 ID 及內容雜湊，以只追加方式記錄。

### 1.7 成功準則（可衡量）

1. **流程成功**
   - 在 ≥ 95% 的專案中，關卡 A（線框圖動態分鏡）會在發生任何商業影片生成前完成並獲批准。
   - 每 60 秒完成影片的平均人工介入次數 ≤ 8（不包括單純批准）。

2. **一致性成功**
   - ≥ 90% 的最終鏡頭無需人工覆蓋，便符合第 1.3 節的所有量化一致性閾值。
   - 整部影片中，任何具名角色的面容身份相似度均不得低於 0.68。

3. **輸出完整性**
   - 三條語言音軌 + 三條字幕軌 + 封裝元素 + YouTube 元資料套件均齊備且在技術上有效。
   - 母帶影片可在 YouTube、Chrome、Safari 及 VLC 正確播放，沒有編解碼器或時間安排錯誤。

4. **審計成功**
   - 可匯出完整製作審計組合並獨立驗證（雜湊相符，提示詞可重建）。

5. **成本及時間成功（以完成 60–90 秒影片為目標）**
   - 可在配備 16 GB VRAM 的機器上，以少於 4 小時實際經過時間完成本機分析 + 線框圖階段。
   - 將商業生成成本控制在用戶定義的預算內（預設建議：使用混合模型製作精緻 60 秒成品，成本 < $25）。

### 1.8 明確非目標（不屬 v1 範圍）

- 即時協作的多用戶編輯。
- 僅根據故事梗概全自動撰寫對白（假定劇本已提供或由故事線推導）。
- 超出現有圖像轉影片模型支援範圍的擬真人類表演捕捉／神經虛擬替身替換。
- 參考素材的自動版權清除。
- 直播或互動式影片生成。

```
PRE-PRODUCTION
0. INPUT  →  1. REFERENCE ANALYSIS  →  2. VISUAL BIBLE  →  3. WIREFRAME  →  4. HUMAN GATE A
                                                                              ↓ (reject)
                                                                         back to Wireframe

PRODUCTION
5. DETAIL/STYLE  →  6. VIDEO GEN  →  7. CONTINUITY + CRITIC  →  8. HUMAN GATE B  →  9. ASSEMBLY
                                              ↑ (reject)                   ↓
                                         re-generate clips            Remotion code

POST + PACKAGING
10. AUDIO (EN / Putonghua / Cantonese)  →  11. SUBTITLES  →  12. PACKAGING  →  13. METADATA  →  14. FINAL GATE → Publish
```

**圖中重點標示的控制點：**
- **關卡 A**（線框圖動態分鏡）是一個*嚴格關卡* — 未獲人手核准動態分鏡前，不得進行任何商業影片生成。
- **關卡 B** 可讓您針對個別鏡頭進行精準重新生成，而無需重新啟動整個流程。
- 連貫性監督代理會執行量化門檻（臉部 ArcFace ≥ 0.72、CLIP ≥ 0.78、光線角度 ≤ 35° 等）。
- 視覺聖經在第 2 階段後會鎖定；任何變更都需要提高版本號，並重新驗證相依鏡頭。
- 多代理層持續運作，並共用製作記憶和已鎖定的護照。

## 3. 完整的改良流程（詳細階段）

### 階段 0 — 輸入準備（已由使用者完成）
- 結構化的故事線文件。
- 附有按順序排列的拍攝指示的場景清單。
- 每項指示均連結至一個或多個 YouTube 參考 URL，並可選擇附註影片中哪一部分相關。

**交付成果：** `storyline.json` + `shots.json`（機器可讀）。

---

### 階段 1 — 參考影片分析與相關片段擷取  
**（低成本、完全本機運行的演算法）**

**目標：** 對每個參考 URL，只下載影片一次，並擷取在時間上連貫且最符合相應拍攝指示的片段。

#### 演算法（建議的本機流程）

1. **下載**
   ```bash
   yt-dlp -f "bv*+ba/b" --merge-output-format mp4 -o "refs/%(id)s.%(ext)s" URL
   ```
   （如已知大約時間，則使用 `--download-sections`）。

2. **轉錄（可選，但價值很高）**
   - 本機 `faster-whisper`（large-v3 或 turbo）→ 詞語層級時間戳記。
   - 儲存為 `refs/<id>.json`。

3. **候選片段生成**
   - 執行 PySceneDetect (ContentDetector) → 硬切清單。
   - 另以 1–2 fps 對影格取樣，以達致密集覆蓋。
   - 產生候選區間（場景邊界 + 4–15 s 的滑動視窗）。

4. **語意評分**
   - 從每個候選區間擷取 3–8 個具代表性的影格。
   - 以 OpenCLIP / SigLIP / MobileCLIP（本機）編碼影格。
   - 使用相同的文字編碼器編碼拍攝指示文字（以及任何「what/how」子項）。
   - 分數 = 影格與指示之間的平均餘弦相似度 + 可選的轉錄文字相似度 + 時間平滑度加分。
   - 優先選擇連續的高分區域，而非零散的高分。

5. **邊界微調**
   - 將得分最高的區間擴展或縮短 ±0.5–1.5 s，使其在相對乾淨的影格開始及結束（如可行，避免在動作中段切換）。
   - 可選擇由人手覆寫開始／結束時間。

6. **剪輯**
   ```bash
   ffmpeg -ss START -to END -i full.mp4 -c copy refs/<id>_relevant.mp4
   ```
   （僅在需要精確影格準確度時重新編碼）。

7. **品質關卡**
   - 捨棄低於相似度閾值的候選項目。
   - 記錄所選區間及其分數。

**工具（全部本機）：** yt-dlp、FFmpeg、PySceneDetect、OpenCLIP / SigLIP、faster-whisper、可選的本機 VLM 作額外驗證。

**交付成果：** 每個相關指示一段乾淨的參考片段 + 中繼資料（時間戳記、分數、轉錄摘錄）。

---

### 階段 2 — 視覺聖經／資產護照鎖定

在進行任何創意生成之前：

1. **實體擷取**
   - Orchestrator + LLM 解析整個故事線 + 指示 → 角色、關鍵道具、地點、重複出現的視覺母題清單。

2. **由參考驅動的資產建立**
   - 根據已擷取的相關片段，生成：
     - 角色轉身設定圖（正面／3⁄4／側面／背面 + 臉部特寫）。
     - 道具參考圖片。
     - 地點／環境圖版。
     - 風格／調色板擷取（主色、光線質感、顆粒感、鏡頭感）。

3. **護照建立**
   - 每個實體均會獲得一份鎖定的「護照」：
     - 標準文字描述（措辭不可變更）。
     - 參考圖片組。
     - 負面描述（其絕不能呈現的樣子）。
   - 護照會儲存在製作記憶中，並逐字複製至其後每個使用該實體的提示詞中。

4. **人工審核關卡（可選但建議）**
   - 在繼續前核准視覺聖經。

**此步驟的原因：** 現代 AI 影片模型在每次生成之間沒有記憶。流程本身必須成為記憶。

---

### 階段 3 — 線框圖／分鏡設計（多代理）

**參與的代理：**
- Shot Designer Agent
- Continuity Supervisor
- Critic Council（構圖、燈光、攝影語言、敘事清晰度）
- Style Director（維持整體美學的一致性）

**每個鏡頭／序列的流程：**

1. Shot Designer 產出：
   - 新鏡頭的詳細文字描述（攝影機、動作、燈光、氛圍），在融入已鎖定的視覺聖經之餘，符合原始指示。
   - 黑白線框圖／草圖關鍵影格（如有需要，包括開始、中段、結束）。首選方法：
     - ControlNet (Lineart / Canny / SoftEdge) + 本機 SD / Flux 模型上的 sketch LoRA。
     - 或純文字轉草圖模型。
   - 連續關鍵影格之間的轉場描述（鏡頭移動、主體動作、燈光變化、光學效果）。

2. Continuity Supervisor 會根據視覺聖經及先前已核准的關鍵影格，檢查身分、道具及環境的一致性。

3. Critic Council 依據評分準則為提案評分，並回傳結構化回饋。

4. 反覆執行，直至所有評論者通過閾值 **或** 人手介入。

5. 生成簡單的轉場線框圖（交叉淡入淡出草圖、動態箭頭，或透過 AnimateDiff / FFmpeg 製作的短動畫變形）。

**此階段的輸出：** 按順序排列、已核准的黑白關鍵影格組 + 轉場描述 + 時間估計。

---

### 階段 4 — 線框圖動態分鏡（人工關卡 A — 最高槓桿）

1. 將所有線框圖關鍵影格 + 轉場組合成低保真動態分鏡影片（FFmpeg 或 Remotion）。
2. 加入暫定時序、簡單音效設計及可選的臨時旁白。
3. 人手審閱完整動態分鏡。
4. 人手可要求更改任何鏡頭或轉場；系統只會將受影響部分返回至階段 3。
5. 只有在明確核准後，流程才會進入成本高昂的生成階段。

**此關卡可避免大部分浪費的生成成本。**

---

### 階段 5 — 為靜態關鍵影格進行詳細風格及色彩處理

- Style Director + 圖像代理會取得每個已核准的線框圖，並製作嚴格遵循視覺聖經的高質素彩色靜態關鍵影格。
- 可生成多個變化版本；由人手或評論者選出保留版本。
- 這些彩色靜態圖會成為影片生成的主要條件圖片（image-to-video / keyframe conditioning）。

---

### 階段 6 — 影片片段生成（模型路由）

- 對每個鏡頭，Orchestrator / DoP agent 會選擇最合適的模型：
  - 長時間連續動作／唇形同步 → Seedance 系列
  - 電影感動態／多鏡頭 → Kling
  - 最高保真度的主打時刻 → Veo
  - 本機／成本敏感 → LTX、Wan、AnimateDiff + ControlNet 等。
- 條件設定：彩色關鍵影格 + 護照文字 + 動態／攝影機描述 + 負面提示詞。
- 如預算容許，每個鏡頭生成 2–4 個變化版本。
- Continuity Supervisor + Critic 會立即為每個 take 評分。

---

### 階段 7 — 一致性與評論循環

- 多模態 Continuity Supervisor 會跨所選 take 重新辨識角色／道具。
- Critic Council 評估動態的自然度、與相鄰鏡頭的燈光連貫性、風格漂移及瑕疵。
- 未通過的鏡頭會自動重新提示（僅作針對性更改）或交回人手處理。

---

### 階段 8 — 人工關卡 B（片段核准）

人手會在動態分鏡的語境下審閱所選影片片段，並可強制重新生成個別鏡頭。

---

### 階段 9 — 最終組裝（首選 Remotion）

- Assembly Agent 編寫／更新 Remotion composition（React 程式碼）。
- 所有影片片段、音訊 stem、時序、轉場、文字疊加均存在程式碼中。
- 好處：代理擅長編寫和編輯 React；人手可開啟 Remotion Studio 並作針對性微調；完全可重現。

替代方案：如不需要以程式碼為基礎的組裝，可使用純 FFmpeg / MoviePy 流程。

---

### 階段 10 — 音訊與多語言語音

1. 按每種語言擷取或生成劇本／對白。
2. TTS：
   - 英語：高質素商業或本機方案（例如 CosyVoice、Tortoise 等）。
   - 普通話：CosyVoice / ChatTTS / 商業方案。
   - 粵語：經微調的 GPT-SoVITS，或同等高質素的本機／商業粵語語音。
3. 音效設計 + 音樂（代理或人手）。
4. 與畫面混音及同步（如適用，進行唇形同步）。

---

### 階段 11 — 字幕

- 為 EN／簡體中文／繁體中文（粵語）生成準確的定時字幕。
- 軟字幕軌（首選）+ 可選的社交平台內嵌版本。
- 風格與整體視覺語言一致。

---

### 階段 12 — 包裝元素

- 從最精彩的時刻生成精華／預告（首 5–15 s）。
- 介紹標誌／片頭。
- 結尾名單（演職員表）。
- 彩蛋（演職員表後的短意外片段）。
- 最終片尾卡／圖片。

全部插入 Remotion composition 或 FFmpeg 時間線。

---

### 階段 13 — 中繼資料與 YouTube 包裝

- 根據場景邊界自動生成章節／斷點。
- 標題、短描述、長描述、標籤。
- 縮圖：最佳關鍵影格（或特別設計的圖片）+ 文字疊加。
- 片尾畫面建議、資訊卡等。

---

### 階段 14 — 最終人工核准及發佈

人手觀看完整母帶。在完成簽核後，Publish Agent 可上載（或交付套件）。

## 5. 實施備註與最佳實務

- 務必**逐幕或逐場景**進行。完整電影的上下文視窗仍會出現偏移。
- 視覺聖經一經鎖定，便應視為不可變更。任何變更均須明確升級版本，並重新驗證下游資產。
- 記錄每次生成（提示詞、種子、模型、分數、獲選／拒絕）。可重現性比原始生成速度更有價值。
- 人類回饋應具備結構（鏡頭 ID + 具體評論），以便代理程式能精準行動。
- 成本控制：線框圖動態分鏡關卡是投資回報率最高的單一決策點。絕不可跳過。
- 粵語內容方面：應及早投資於高品質語音（GPT-SoVITS 微調或同等級商業方案）。唇形同步的準確度對最終潤飾十分重要。

## 6. 下一步即時行動

1. 將現有故事線及拍攝指示轉換為嚴格的 `storyline.json` + `shots.json`。
2. 實施第 1 階段本地擷取管線（yt-dlp → Whisper → CLIP 評分 → FFmpeg 剪輯），並在 3–5 段參考影片上進行測試。
3. 建立視覺聖經擷取代理程式及人工審核 UI，用於角色／道具／風格護照。
4. 建立多代理程式編排器，配備連貫性監督員 + 評審委員會。
5. 製作線框圖 → 動態分鏡路徑的原型（ControlNet 草圖 + FFmpeg/Remotion 組裝）。

此計劃旨在達至可投入製作、具成本意識、以一致性為先，並全面配合 2026 年代理式 AI 電影製作系統所觀察到的最佳實務。
